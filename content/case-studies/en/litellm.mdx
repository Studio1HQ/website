Studio1 partnered with **LiteLLM** to revamp the docs experience across the LiteLLM **SDK** and **Gateway**. The goal was simple: reduce friction for new developers, make advanced capabilities easier to discover, and turn documentation into a stronger product adoption surface.

The work combined **documentation strategy, information architecture, technical writing, and community feedback loops**. The outcome was a docs experience that gets developers to a first working request faster, tells them clearly whether they need the SDK or the Gateway, and keeps them exploring with less friction: a revamp LiteLLM's CEO endorsed publicly.

## About LiteLLM

[**LiteLLM**](https://github.com/BerriAI/litellm) is an open-source developer platform that gives teams one OpenAI-compatible interface to work with **100+ LLM providers**. Developers use it as a lightweight SDK inside applications, or run it as a shared **LLM Gateway** with routing, virtual keys, spend tracking, logging, and guardrails.

With that surface area: providers, models, proxy workflows, integrations, documentation isn't a support asset. It's the primary adoption surface. Developers need to know not just what LiteLLM can do, but where to start and which path matches their setup.

## The challenge: growth outpacing the docs

LiteLLM was growing quickly, and that growth created a familiar DX problem:

* New users needed a clearer path to their **first successful request**
* Developers were choosing between **SDK** and **Gateway** paths without enough guidance
* Tutorials, integrations, release notes, and feature references needed stronger structure and categorization
* Community questions kept surfacing repeat friction points that could be clarified in docs and DX

The brief was not a visual refresh. It was making the entire experience easier to navigate, easier to learn, and easier to adopt.

## Our role

Studio1 operated as LiteLLM's embedded documentation and DX team:

* **Documentation strategy**: deciding what the docs needed to do for adoption, not just coverage
* **Information architecture**: restructuring navigation around how developers actually evaluate the product
* **Technical writing**: new quickstarts, guides, and integration content
* **Community support**: answering real developer questions and feeding recurring patterns back into docs and product

## What we delivered

### 1. A clearer documentation architecture

We restructured the docs so developers could understand the product faster and navigate with confidence:

* A new **Learn** section as the main starting point for new users
* Clear separation between **SDK** and **Gateway** journeys
* Dedicated **Guides** and **Tutorials** hubs: reference content vs. step-by-step workflows
* Improved categorization across **Integrations** and supporting feature areas
* Better homepage structure, sidebar organization, and discovery paths

## The results

For developer tools, better docs do more than explain features, they shorten time-to-value and get more users to the moment where the product clicks. For LiteLLM, that meant:

* **Less confusion at the top of the funnel**: one clear starting point instead of scattered pages
* **Faster onboarding into the right product path**: SDK or Gateway, decided in minutes
* **Better discoverability** of integrations and advanced features
* **A public CEO endorsement** of the revamped experience
* **Stronger feedback loops** between the community, the docs, and the product team

The documentation now does what adoption-stage docs should: turn curiosity into activation, and activation into deeper usage.

## Why it worked

Docs revamps fail when they're treated as reorganization exercises. This one worked because it was built around **how developers evaluate and adopt LiteLLM**: the first request, the SDK-or-Gateway decision, the integration they came to set up, and because community questions were treated as a roadmap, not noise.
