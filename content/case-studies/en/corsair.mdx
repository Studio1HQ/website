Studio1 worked with **Corsair**, an open-source integration layer for AI agents, while the product was still early. The work started with an onboarding audit and an example project, then shifted toward community events, hackathons, and posts aimed at getting developers to try the product.

The goal was not simply attention. Corsair needed a shorter path to a first working call, a concrete example of the product in use, and communities that would actually build with it.

## About Corsair

[**Corsair**](https://corsair.dev) is an open-source TypeScript layer that lets an agent use third-party apps without holding the credentials. Permissions sit in front of every call, and the same layer works for agents, backend jobs, and product UI.

Because Corsair sits between an agent and real accounts, developers do not adopt it off a feature list. They need a fast first session and a reason to trust it, which made developer experience and examples as important as promotion.

## The challenge: an early repo that still had to feel finished

Corsair needed a growth motion that could:

* Shorten the first session in the hosted app and the docs
* Give builders a concrete example instead of a blank integration list
* Reach developers who would actually try the product
* Reach live developer communities, not only post into feeds

The brief was developer experience and community growth working together: a smoother product first, then the people to try it.

## Our role

Studio1 supported Corsair across the developer-facing motion:

* **Onboarding audits** of the hosted app, the docs, and the first-run flow
* **Example projects and demos** that showed Corsair in a real workflow
* **Onboarding improvements** across the hosted app, docs, and learning platform
* **Pricing research** to help decide how the site should present plans
* **Docs and GitHub README improvement** driven by audit and community feedback
* **Community events and hackathons**, coordinated with developer communities
* **Technical posts** on Reddit, X, LinkedIn, and daily.dev
* **Contributor feedback**, reviewing community-built integrations for tests, docs, and wiring

## What we delivered

### 1. Onboarding audits

We audited the first-run experience the way a new developer would meet it, then wrote up specific fixes:

* Open the dashboard on a getting-started guide, with a way to make a test request in the product
* Show a connected user only the integrations they set up, not the whole catalog
* Lead setup with the hosted app so the first response arrives before the long self-hosted path
* Surface the docs' MCP endpoint as part of onboarding instead of a hidden extra

The Corsair team used the first audit to rework the hosted app and a quick start that reaches a working example in under a minute. A second audit followed after the new flow shipped.

### 2. Example projects and demos

Developers trust a layer like Corsair when they can see it working, so we built demos that use it in real workflows.

**[Brieflane](https://github.com/Studio1HQ/brieflane)** turns meeting transcripts into Linear issues, risks, decisions, and Slack updates, built with Next.js, Corsair, and OpenAI Agents. We shared it as an open-source demo with a walkthrough video.

### 3. Onboarding, pricing research, docs, and README

Beyond the first audit, we helped improve onboarding on more than one surface, including Corsair's learning platform, not only the hosted app. We also researched how comparable products present pricing to help decide how Corsair's site should do it, and fed audit and community feedback back into the docs so the fixes stayed in place.

We also worked on a detail that is easy to underestimate: the **GitHub README**. For an open-source project it is the front door, so we improved it to make Corsair easier for everyone to understand: a clear one-line description, key links up front, and the product shown in action.

### 4. Community events and hackathons

Alongside the audits and demos, we moved from posts to people. Studio1 coordinated with multiple developer communities, planned hackathon deliverables, and joined student events as mentors, with a dedicated Corsair track. Hackathons gave builders a reason to try the product, and many of them starred it afterward.

Stars grew from about 300 in mid-May to 1,000 in early June and 2,000 by mid-June.

### 5. Technical posts and community distribution

Alongside the events, we kept a steady stream of posts going. An article on why every extra MCP server makes an agent slightly worse was adapted for several agent and MCP communities on Reddit, with companion posts on X, LinkedIn, and daily.dev. The posts led with a problem developers recognize and pointed to Corsair as one answer.

## The results

* **2,000 GitHub stars**, up from about 300 in roughly five weeks, with 1,000 crossed in early June
* **A faster first session**, after two onboarding audits led to a reworked hosted app and a quick start
* **Demos developers could run**, including Brieflane and SlideFlow, shared as open-source examples
* **A clearer front door**, with an improved README, docs, and learning-platform onboarding
* **Pricing research** that informed how the site presents plans
* **Student hackathons and community events** with Corsair on site as a mentor
* **Technical posts** on Reddit, X, LinkedIn, and daily.dev that carried the story beyond the repo

Star counts come from the public repo history during the engagement. We do not claim growth after it ended.

## Why it worked

Developer experience came first, so the people who arrived found a product that was easy to try. The example project showed what Corsair was for, and the hackathons gave builders a reason to use it. We put time into communities and events, not only more content.

For an early open-source project, that order matters. A shorter first session, a real example, and the right rooms produce stars from people who stay.
