**The short answer:** Hire a full-time technical writer if docs are your product's front door: a large API or SDK surface, releases every sprint, and reference pages that go stale when the API changes. Hire a technical content agency if what you lack is reach: tutorials, comparisons and launch content that bring in new developers within weeks, often with distribution. If your docs are small and stable, the gap is usually marketing content, not docs headcount. Many devtools end up hybrid: one in-house owner, plus an agency for volume and launches.

## A docs writer and a content writer do two different jobs

Most "technical writer vs agency" debates compare two different jobs.

**The docs job.** The US Bureau of Labor Statistics says technical writers [determine the needs of users of technical documentation, talk with product designers and developers, and collect user feedback to improve content](https://www.bls.gov/ooh/media-and-communication/technical-writers.htm). In a devtool, that means the quickstart, API reference, SDK guides and error pages. Many teams structure it with [Diátaxis](https://diataxis.fr/) (tutorials, how-to guides, reference, explanation) and run it as [docs as code](https://www.writethedocs.org/guide/docs-as-code/): Markdown in Git, code review, automated tests. It matters: in Stack Overflow's 2025 survey, [67.8% of developers learned to code from technical documentation in the past year](https://survey.stackoverflow.co/2025/developers), more than from any other resource.

**The content-marketing job.** This engineer-writer writes for developers who have not found you yet. Permit.io's guide "How to Implement RBAC in Supabase" is an example: it answers a question developers type before they have heard of Permit.io. Our [technical content marketing guide](/blog/technical-content-marketing-for-devtools) covers what that job produces at each stage of the developer journey.

| | Docs technical writer | Content-marketing engineer-writer |
| --- | --- | --- |
| Reader | Developers already trying your product | Developers who have not found you yet |
| Output | Quickstart, API reference, SDK guides | Tutorials, comparisons, integration guides, launch posts |
| Lives in | Docs site, usually a Git repo | Blog, Dev.to, Medium, community threads |
| Ships | With each release | On a calendar and around launches |
| Measured by | Setup completion, support tickets | Docs clicks and signups from each piece |
| Fails when | Docs drift from the API | The code doesn't run, or nobody posts it |

**Before and after: the job title.**

* **Before:** "Technical Writer (docs, blog, social)." One person, two jobs, and you get one of them.
* **After (docs):** "Technical Writer, API Docs. Owns the quickstart and API reference in our docs repo and ships docs with each release."
* **After (content):** "Developer Content Engineer. Writes two tutorials a month with runnable code and posts each one where its readers are."

**Key pointers:**

* Write down which job you are filling before you post a role or brief an agency.
* Put the docs job inside the engineering workflow: the docs PR merges with the feature PR.
* Judge content on docs clicks and signups per piece, as in our guide to [measuring content ROI beyond pageviews](/blog/developer-tool-content-roi-beyond-pageviews).

## The five options, and what each is good at

**1. A full-time technical writer.** Good at owning the docs for years, sitting in sprint planning and catching API changes before release. Weak at marketing volume and distribution: it is one person with one calendar, usually hired for docs, not search.

**2. Freelance technical writers.** The BLS notes that some technical writers freelance, usually on [short-term or recurring assignments such as writing about a new product](https://www.bls.gov/ooh/media-and-communication/technical-writers.htm). Good at single pieces in a niche stack. Weak at strategy and consistency: with three freelancers, you become the managing editor.

**3. A technical content agency.** Good at volume, writers matched to different stacks, topic research, editing, launches and distribution. Packages vary. Infrasity's Starter plan lists [4 long-form blogs and 1 SDK guide or integration walkthrough a month](https://www.infrasity.com/pricing). Draft.dev says it drafts [with AI workflows, from a network of 300+ engineers, and has every piece reviewed by developers](https://draft.dev/). Studio1 uses its own engineers and writers; our comparisons with [Draft.dev](/compare/studio1-vs-draft-dev) and [Infrasity](/compare/studio1-vs-infrasity) show the differences. Weak at deep product knowledge on day one and at docs that change every sprint.

**4. Engineers writing.** Good at credibility and at posts only insiders can write: architecture deep dives, benchmarks, postmortems. Write the Docs notes that with docs as code, ["developers will often write a first draft of documentation"](https://www.writethedocs.org/guide/docs-as-code/). Weak at consistency, because posts lose to roadmap work.

**5. Hybrid.** One owner inside the company plus outside writers for volume, launches or distribution. More on this below.

**Key pointers:**

* Use a full-time writer for the docs surface, and an agency or freelancers for the marketing surface.
* Give engineers the two or three posts a quarter only they can write, plus an editor.
* Hire freelancers only if someone in-house can brief, edit and schedule them.

## What does each option cost?

**A full-time technical writer.** The BLS lists [median pay of $90,390 a year, or $43.46 an hour, in May 2025](https://www.bls.gov/ooh/media-and-communication/technical-writers.htm). That median covers every industry that hires technical writers, manufacturing included, so check your local market. In June 2026, wages were [70.0% of private employers' compensation costs, and benefits the other 30.0%](https://www.bls.gov/opub/ted/2026/compensation-costs-for-private-industry-workers-averaged-46-89-per-hour-worked-in-june-2026.htm). Divide the salary by 0.70 and the median becomes about **$129,000 a year**, or $10,800 a month, before recruiting fees.

**Engineers writing.** The BLS median for software developers is [$135,980 a year (May 2025)](https://www.bls.gov/ooh/computer-and-information-technology/software-developers.htm), about $93 an hour loaded. If a code-heavy tutorial takes an engineer two days, that is about $1,500, plus the feature that didn't ship.

**Freelancers** price per piece, per hour or per word. The BLS pay data excludes self-employed workers and we haven't found a public benchmark we trust, so get three quotes for the same brief.

**Agencies** usually charge a monthly retainer priced by volume and scope, often with a minimum term or a trial. Draft.dev lists [a three-month minimum](https://draft.dev/); Infrasity offers [a 30-day proof of concept](https://www.infrasity.com/pricing). Studio1 quotes by scope and doesn't publish a price list. For the DevRel version of this math, see [DevRel agency vs in-house DevRel hire](/blog/devrel-agency-vs-in-house-devrel-hire).

**Template: cost worksheet (fill in your numbers)**

| Line | Full-time writer | Freelancers | Agency | Engineers |
| --- | --- | --- | --- | --- |
| Base cost | Salary divided by 0.70 | Rate times pieces | Monthly retainer | Hours per piece times loaded rate |
| One-off cost | Recruiting fee, tools | Trial pieces | Onboarding, minimum term | None |
| Your review time | A few hours a week | More: you edit too | A few hours a week | Peer review |
| Distribution | Separate owner | Separate owner | Ask if included | Usually nobody |

**Key pointers:**

* Compare loaded cost, not salary: divide any salary by 0.70 first.
* Ask every agency what is excluded, the minimum term, and who owns the content when you stop.
* Price engineer hours before deciding engineers will "just write the blog".

## How long until the first piece ships?

| Option | Steps before the first piece | Time, with source |
| --- | --- | --- |
| Full-time writer | Recruit, notice period, product ramp | We found no verified time-to-hire figure for technical writers. As a proxy, senior software engineers take [47 days from requisition to accepted offer](https://www.recruitingfromscratch.com/blog/how-long-does-it-take-to-hire-a-senior-software-engineer-in-2026), before notice and ramp |
| Freelancer | Find, paid trial, brief | Depends on sourcing. Budget one paid trial piece |
| Agency | Kickoff, outline approval, draft, your review | Draft.dev: [first pieces within 3 weeks of kickoff](https://draft.dev/). Infrasity Starter: [7 to 10 days per post](https://www.infrasity.com/pricing). Studio1: 3 to 7 days from brief to draft for straightforward blogs and tutorials, 10 to 14 for code-heavy guides |
| Engineers | Whenever the sprint allows | Competes with roadmap work every week |

All of these assume your reviewer replies fast. A draft that waits two weeks for sign-off is two weeks late, whoever wrote it.

**Key pointers:**

* Launching in the next 6 to 8 weeks? A new hire won't be ready. Use an agency or a freelancer you already trust.
* Agree on a review turnaround (for example, 2 business days) before the first draft arrives.
* Approve outlines, not just drafts. A wrong angle caught at the outline saves a rewrite.

## What you need internally, whichever you pick

**Checklist: day-one setup for any writer**

1. **A sandbox account** with the features they will cover, plus API keys they can burn.
2. **A named technical reviewer** with time on the calendar and an agreed turnaround.
3. **Publishing access** to the docs repo or CMS, and a person who merges or publishes.
4. **A style guide:** yours, or [Google's developer documentation style guide](https://developers.google.com/style) as a default.
5. **A topic list tied to a goal.** Ten real questions from sales calls, support tickets or Discord beat a keyword list.
6. **A distribution owner** for each piece, named before it is written.
7. **Ownership in writing:** content, code samples and accounts stay in your repos and accounts.

**Key pointers:**

* Book the reviewer's time before you sign or hire anyone.
* Give writers the sandbox a new customer gets. Their friction is your users' friction.
* Keep a running list of developer questions and feed it to whoever writes.

## Which option fits your stage and need?

| Your situation | Best fit | Watch out for |
| --- | --- | --- |
| Seed stage, docs are a quickstart and a README | Engineers own docs; agency or freelancer for a few tutorials | Founder time going to editing |
| Launch in the next 6 to 8 weeks | Agency with launch experience | Content with no plan for launch day |
| API or SDKs change every sprint and docs drift | Full-time docs technical writer | Hiring a marketing writer for this |
| You need search and comparison traffic | Agency or a content-marketing engineer-writer | Reports that stop at pageviews |
| Large docs surface, several products or SDKs | Full-time docs writer or team, plus an agency for marketing | Asking the docs team to also run the blog |
| You already have a DevRel lead or content owner | Hybrid: owner plus agency for volume and launches | An agency with nobody to report to |

### When a full-time technical writer is the better choice

Hire one when your product is docs-heavy (developers live in the reference), when your API changes constantly (docs that ship a sprint late are wrong for a sprint), or when your docs surface is large. Cloudflare's developer docs live in a [public GitHub repo with more than 26,000 commits](https://github.com/cloudflare/cloudflare-docs), and Cloudflare's Adam Schwartz calls Diátaxis ["our north star for information architecture"](https://diataxis.fr/) in the redesign of its developer docs. That is permanent work, not a project. An agency can fix a quickstart, write missing guides or audit the docs, but it should not be the only owner of a reference that changes weekly.

![Cloudflare's cloudflare-docs GitHub repository on its production branch, with 26,586 commits and developers.cloudflare.com as its site](/blog/uploads/technical-writer-vs-content-agency/cloudflare-docs-repo.webp "A large docs surface run as code: work a full-time docs team owns, not a project.")

**Key pointers:**

* Count your docs pages and releases per month. If both are high, open the docs role now.
* If your docs are small and stable, spend the first budget on reach.
* Revisit the decision at each funding round.

## Red flags when hiring each option

| Option | Red flag | How to test it |
| --- | --- | --- |
| Any writer | No code samples in the portfolio | Ask for two pieces with code, then clone and run one |
| Any writer | Can't run your product | Paid trial with a friction log (template below) |
| Content writer or agency | No distribution plan | Ask "where does this go after it's published, and who posts it?" |
| Docs writer | Has never worked in a Git and PR workflow | Ask for a merged docs pull request |
| Agency | The person on the sales call won't write for you | Ask for the named writer and their samples |
| Agency | Can't say how AI is used, or who runs the code | Ask. In Stack Overflow's 2025 survey, [46% of developers distrust the accuracy of AI tools](https://survey.stackoverflow.co/2025/ai), and your readers will notice |
| Engineers | No time blocked for writing | Check the sprint plan, not the promise |

**Template: paid trial brief (copy and edit)**

```text
Paid trial: [Product] technical writer

Task: a 1,200 to 1,800 word tutorial, "How to [do X] with [Product] and [popular tool]".
Setup: use the sandbox account below. Start from our public quickstart, not from us.

Deliver:
1. The draft in Markdown. Every code sample runs, in a repo or gist we can clone.
2. A friction log: each step where you got stuck, guessed or hit an error, and how long it took.
3. A distribution plan: three places this piece should go, and the title you would use in each.

Timebox: [N] hours, paid at your normal rate.
Reviewer: [name], who replies within 2 business days.
```

One task tests all three red flags: whether the code runs, whether they can use your product, and whether they think past the publish button.

**Before and after: a trial piece's opening line.**

* **Before:** "Authorization is an important part of modern applications."
* **After:** "By the end of this guide, a viewer in your Supabase app can read documents but not delete them, and you can change that rule without a redeploy."

**Key pointers:**

* Never hire a writer or sign an agency without a paid trial on your own product.
* Read the friction log before the draft. It shows how they work.
* Ask every agency for the named writer and how AI fits into their process.

## The hybrid model: an in-house owner plus an agency

Hybrid works when one person inside knows the product and decides what gets made, and outside writers make more of it. It breaks when nobody inside owns it. Permit.io, in the next section, is one example.

**Template: who owns what**

| Work | In-house owner | Agency |
| --- | --- | --- |
| Strategy and priorities | Owns | Proposes topics from search and community research |
| API reference and docs structure | Owns | Fixes and small guides on request |
| Tutorials, comparisons, integration guides | Approves outlines, signs off | Writes, tests the code, revises |
| Launch content | Sets the date and message | Produces posts, demos and assets |
| Distribution | Posts where the team's own voice matters | Syndication to Dev.to and Medium, social copy |

Use the agency for what one owner can't scale alone: **volume** (a tutorial series or comparison set), **launches** (a fixed date and many assets) and **distribution**, which our [channel-by-channel distribution playbook](/blog/how-to-distribute-technical-content-reddit-x-youtube) covers. If the owner seat is empty, [fractional DevRel](/blog/fractional-devrel) is one way to fill it.

**Key pointers:**

* Name the in-house owner before you sign. An agency with nobody to report to guesses at your product.
* Keep the reference docs in-house. Send out work with a deadline or a volume target.
* Review the split each quarter, and bring routine work in-house.

## FAQ

### How much does it cost to hire a technical writer?

The BLS puts median pay for technical writers at $90,390 a year, or $43.46 an hour, as of May 2025. Benefits were 30% of private employers' compensation costs in June 2026, so a median writer costs about $129,000 a year loaded. It covers all industries, so check your local market.

### Should I hire a technical writer or an agency?

Hire a full-time technical writer if your docs are large, your API changes often and developers live in the reference. Hire an agency if you need tutorials, comparisons and launch content within weeks, with distribution. If you already have an in-house owner, a hybrid usually works best.

### Is a technical writer the same as a content marketer?

No. A docs technical writer keeps the quickstart, reference and guides correct for developers already using your product. A content-marketing engineer-writer writes tutorials and comparisons that bring in developers who haven't found you yet. Say which one you need in the job title.

### Can a content agency write our API documentation?

It can handle parts of it: quickstart fixes, guides, code examples and audits. It should not be the only owner of a reference that changes every sprint, because docs need to ship with each release. Keep a docs owner in-house and use the agency for defined docs projects.

### Should our engineers write the blog?

Engineers should write the posts only they can write, such as architecture deep dives, benchmarks and postmortems, with an editor's help. As the main content engine it rarely holds up, because writing loses to roadmap work and a loaded engineering hour costs about $93 at the BLS median.

### How do I test a technical writer before hiring?

Run a paid trial on your own product. Ask for a short tutorial with runnable code, a friction log of every step where they got stuck, and three places the piece should be distributed. That one task shows whether they can code, use your product and think about distribution.
