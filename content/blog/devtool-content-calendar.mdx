**The short answer:** A devtool should plan content from evidence, not brainstorms. Pull topics from Search Console queries, support tickets, GitHub issues, sales calls, Reddit and Hacker News threads, and the prompts developers type into AI assistants. Give each piece one job (discover, evaluate, activate or expand), set a cadence your engineer reviewers can sustain, and pin the plan to release dates. Work in 12-week blocks, with a target query, owner, reviewer, channels and CTA on every row, and cut or double down monthly.

## Where do devtool content ideas come from?

Your best topics already exist in the developer's own words. Log each idea with a link to where you found it.

### 1. Google Search Console queries

Open Performance, then Search results, on the Queries tab. Add a Query filter, choose Custom (regex), then Matches regex. Search Console uses RE2 syntax and isn't case-sensitive by default ([Google's filtering docs](https://support.google.com/webmasters/answer/17011165)). Try these two:

```text
^(how|what|why|which|when|can|does|is)\s
(\svs\s|versus|alternative|compare)
```

Sort by Impressions. A question you appear for without a page that answers it is a topic. Then set the Query filter to Non-branded to see what strangers search for.

### 2. Support tickets and sales calls

Export 90 days of tickets and tag each one by the task the developer was attempting ("retry a failed job"), not by product area. The five most common tasks become tutorials, and the exact error strings become titles. In sales call notes, search for "does it support" (integration guides), "how do you compare to" (comparison pages) and "we tried" (migration guides).

### 3. GitHub issues and discussions

Search your repo, a competitor's, and the upstream frameworks your users build on, with GitHub's [issue qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests), [discussion qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-discussions) and [sort options](https://docs.github.com/en/search-github/getting-started-with-searching-on-github/sorting-search-results):

```text
repo:your-org/your-repo is:issue label:question sort:comments
repo:upstream-org/framework is:issue "background jobs" in:title reactions:>10
repo:your-org/your-repo is:unanswered comments:>2
```

Run the last one as a Discussions search: an unanswered thread with several comments is a shared question nobody has written up.

### 4. Reddit and Hacker News threads

On Reddit, search your category inside the subreddit your users read, sort by Top for the past year, and scan the comments for "we switched from" and "I wish". For Hacker News, bookmark [HN Search API](https://hn.algolia.com/api) queries for stories above 50 points and for Ask HN threads:

```text
https://hn.algolia.com/api/v1/search?query=background%20jobs&tags=story&numericFilters=points>50
https://hn.algolia.com/api/v1/search?query=background%20jobs&tags=ask_hn
```

### 5. The prompts developers type into AI assistants

In Stack Overflow's [2026 Developer Survey](https://stackoverflow.blog/2026/10/06/the-results-of-the-2026-developer-survey-are-here/), 83% of respondents said they search online for answers and 70% ask an AI agent. Write 10 to 12 prompts a developer would type before they know your name ("how do I retry failed background jobs in Node without Redis?"), run each in ChatGPT, Perplexity and Gemini with web search on, and log the cited pages. Where a competitor or forum thread is cited and you aren't, you have a topic. Our [AI visibility audit](/blog/how-to-measure-devtool-visibility-in-ai-answers) has the method.

**Key pointers:**

* Keep the developer's exact phrasing, error text included, as the working title, with the source link beside it.
* Rerun the Search Console regex and the GitHub searches on the first Monday of each month.

## What mix should you publish, and how often?

Give every piece one job. Studio1's Tensorlake case study puts it plainly: "This was not a publishing calendar for its own sake. Each piece had a job." Our [technical content marketing guide](/blog/technical-content-marketing-for-devtools) covers each content type in depth.

| Job | The reader | Piece types | Judge it by | Studio1 example |
| --- | --- | --- | --- | --- |
| Discover | Has the problem, doesn't know you | Explainers, trend pieces, demo projects | Non-branded impressions and clicks | Tensorlake's [TOON vs JSON](https://www.tensorlake.ai/blog/toon-vs-json) |
| Evaluate | Is comparing options | Comparisons, integration guides | Clicks to docs and pricing | Webcrumbs' [v0 comparison on DEV](https://dev.to/arindam_1729/i-found-a-tool-even-better-than-v0-you-wont-believe-what-it-can-do-igf) |
| Activate | Is trying your product | Tutorials, quickstarts, sample repos | Signups and first successful API calls | Permit.io's [RBAC in Supabase guide](https://www.permit.io/blog/how-to-implement-rbac-in-supabase) |
| Expand | Already uses it | Launch posts, migration and advanced guides | Feature adoption, fewer tickets on the topic | Entelligence AI's feature-launch blogs |

Tilt toward the weakest job: if few signups reach a first API call, add activate pieces, and if non-branded impressions are flat, add discover pieces.

### Cadence by team size

Cadence is capped by engineer review time, not writing time, and it only compounds if you hold it ([why software companies invest in content](/blog/why-software-companies-invest-in-content)). Push past it and quality slips: in CMI's [2027 B2B trends research](https://contentmarketinginstitute.com/articles/b2b-content-marketing-trends-research-2), 65% of B2B marketers said they faced increased pressure to produce content faster, and 29% of those said the result was more generic content. Starting points:

| | Solo founder | One in-house writer | Agency |
| --- | --- | --- | --- |
| Realistic cadence | 2 pieces a month | 1 a week | 2 to 3 a week across two tracks |
| Monthly mix | 1 tutorial, 1 comparison or explainer | 2 activate or evaluate, 1 discover, 1 refresh | A growth track and an implementation track |
| Who runs the code | A cofounder or a power user | One named engineer, 2-day SLA | The agency's reviewer, then your engineer |
| Skip for now | Edited video; record the terminal instead | A newsletter until there's a backlog | Topics nobody on your team can review |

**Key pointers:**

* Tag every post you've already published with one job, then fill the emptiest job first.
* Book your reviewer's hours before you commit to a cadence.

## How do you anchor the calendar to releases and launches?

Put release dates on the calendar before any topic. Your own come from the roadmap; your ecosystem's are public. Python ships a feature release every October, with the feature freeze (beta 1) usually in late May ([PEP 602](https://peps.python.org/pep-0602/)). Kubernetes releases "approximately three times per year" ([Kubernetes release cycle](https://kubernetes.io/releases/release/)). If your SDK runs on either, your compatibility post has a date months ahead.

![Kubernetes release cycle diagram: feature freeze around week 4, code freeze around week 12 and release around week 16 of a four-month cycle](/blog/uploads/devtool-content-calendar/kubernetes-release-cycle.webp "Ecosystem release calendars are public. Put them on your content calendar before any topic.")

**Template: the launch-anchored sequence**

| When | Piece | Why then |
| --- | --- | --- |
| 3 weeks before | Explainer on the problem the feature solves | Launch posts need something to link |
| 1 week before | Docs, quickstart and demo repo finished | Launch traffic lands on something that works |
| Launch week | Launch post and demo video, one channel per day | Each channel gets its own day |
| 1 week after | Migration guide or a "how we built it" deep dive | Users upgrade, and engineers explain trade-offs |
| 2 to 4 weeks after | Tutorial answering the top launch questions | The comments show what was unclear |

Supabase planned launch weeks on a similar clock: press "needs to be organized up to 3 weeks before you plan to Launch" ([Supabase](https://supabase.com/blog/supabase-how-we-launch)).

### Evergreen vs timely pieces

Evergreen pieces (tutorials, integration guides, comparisons) earn search traffic for months and need upkeep. Timely pieces (a new model, format or framework release) win a short window. Tensorlake's [TOON vs JSON](https://www.tensorlake.ai/blog/toon-vs-json), published December 9, 2025, as the format became a topic of interest, surfaced in Google results beside established technical sources. When you refresh an evergreen post, rerun the code and bump the versions. Google's [helpful content guidance](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) asks, "Are you changing the date of pages to make them seem fresh when the content has not substantially changed?"

**Key pointers:**

* Enter every release date you know, yours and your ecosystem's, before you add a topic.
* Leave one slot a month empty for news, and link timely posts to an evergreen piece instead of rewriting them later.

## A 12-week devtool content calendar template

**Example only.** Acme is a made-up background-jobs SDK for Node.js and Python that ships version 2.0 in week 7. Replace every row with topics from your own sources.

| Week | Piece | Type | Target query or AI prompt | Owner | Reviewer | Distribution channels | CTA |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | Retry failed jobs with exponential backoff in Node.js | Tutorial (activate) | "retry failed jobs node" | Writer | Backend eng | Blog, DEV, X | Copy the install command |
| 2 | Acme vs Competitor X for Node.js job queues | Comparison (evaluate) | "competitor x alternative" | Writer | Eng lead | Blog, Reddit, newsletter | Open the quickstart |
| 3 | Why jobs run twice, and how idempotency keys fix it | Explainer (discover) | Prompt: "why does my background job run twice" | Writer | Backend eng | Blog, Reddit, LinkedIn | Read the retries docs |
| 4 | Background jobs in Next.js route handlers | Integration guide (evaluate) | "next.js background jobs" | Writer | Frontend eng | Blog, DEV, X | Clone the example repo |
| 5 | Cron vs a job queue: when to use each | Explainer (discover) | "cron vs job queue" | Writer | Eng lead | Blog, LinkedIn | Join the 2.0 beta |
| 6 | Refresh week 1's tutorial for 2.0, finish the docs | Refresh (activate) | Existing query | Writer | Backend eng | Newsletter | Try the 2.0 beta |
| 7 | Acme 2.0: cron schedules and a Python SDK | Launch post (expand) | Branded | Founder | Eng lead | Blog, HN, Reddit, X, LinkedIn | Read the upgrade guide |
| 8 | Upgrading from Acme 1.x to 2.0 | Migration guide (expand) | "acme 2.0 upgrade" | Eng lead | Writer | Blog, docs, Discord | Follow the upgrade steps |
| 9 | Open slot | Timely | Whatever is news that week | Writer | Eng lead | Set per piece | Set per piece |
| 10 | Background jobs in FastAPI with Acme | Tutorial (activate) | "fastapi background job queue" | Writer | Python eng | Blog, DEV, YouTube Short | Copy the pip command |
| 11 | A video-transcoding pipeline with Acme and FFmpeg | Demo project (discover) | Prompt: "how do I queue ffmpeg jobs in python" | DevRel | Backend eng | GitHub, X video, Reddit, HN | Star the repo |
| 12 | Part 2 of the month's best performer | Picked at the monthly review | From Search Console | Writer | Part 1's reviewer | Same as part 1 | Same as part 1 |

Weeks 1 to 4 fill gaps your sources found, and weeks 5 to 8 follow the launch sequence above. The mix is 3 discover, 2 evaluate, 3 activate and 2 expand pieces, plus two flexible slots.

**Key pointers:**

* Fill the Reviewer column before the Piece column, and drop any row nobody can review.
* Give each row one CTA, and make it a technical next step, not "book a demo".

## How do you repurpose one tutorial across a week?

Rebuild the blog post for each channel, one channel a day. Here is the week 1 tutorial:

| Day | Format | What it looks like |
| --- | --- | --- |
| Tuesday | Blog post | The full tutorial with tested code, as the canonical home |
| Wednesday | X thread | 5 to 7 posts: the failure, the fix, a 20-second screen recording, the link last |
| Thursday | Reddit post | Problem-first post in one subreddit, code inline, link last if the rules allow |
| Friday | DEV republish | The full post, with `canonical_url` pointing to your blog |
| Next Tuesday | Short video | 45 to 90 seconds of the retry working, filmed vertical |
| Next newsletter | Newsletter item | Three lines: the problem, the fix in one sentence, the link |

DEV's [editor guide](https://dev.to/p/editor_guide) defines `canonical_url` as the "link for the canonical version of the content", and YouTube counts vertical or square videos up to three minutes as Shorts ([YouTube Help](https://support.google.com/youtube/answer/15424877)). Each channel's rules are in our [distribution playbook](/blog/how-to-distribute-technical-content-reddit-x-youtube). For canonical setup on DEV, Hashnode and Medium, read [where to cross-post technical articles](/blog/cross-posting-dev-to-hashnode-medium).

**Before and after: the hook**

* Before: "New on our blog: how to retry jobs with Acme."
* After: "Your job failed at 2 a.m. and retried 500 times in a minute. Here's exponential backoff in 15 lines of Node.js."

**Key pointers:**

* Write the hook from the failure the tutorial fixes, not from the product name.
* Put the repurposing days in the calendar row, so each version has an owner and a date.

## What review workflow and SLAs keep the calendar on time?

Studio1's workflow runs from topic to an approved outline, then the draft, an internal review, the client's review, revisions and publishing. Most straightforward tutorials move from brief to draft in 3 to 7 days ([technical content marketing](/technical-content-marketing)). Here it is as SLAs:

| Stage | Who | SLA | Done when |
| --- | --- | --- | --- |
| Outline | Writer drafts, content owner approves | 2 business days to approve | Target query, angle and code plan agreed |
| Draft | Writer | 3 to 7 days, or 10 to 14 for code-heavy guides | Every code block runs for the writer |
| Technical review | An engineer who didn't write it | 2 business days | They followed every step in a clean environment |
| Edit | Editor or content owner | 1 business day | Title, short answer, links and CTA checked |
| Final approval | One named approver | 1 business day | Approved and scheduled |

**Key pointers:**

* When a stage misses its SLA, the piece drops back one slot and the next ready piece moves up.
* Allow one review round per stage, with every comment in the doc at once.
* Approve outlines, not finished drafts, so technical objections arrive before the writing.

## The monthly review: what to cut and what to double down on

Block 45 minutes on the first Monday of the month:

1. In Search Console's Performance report, open the date filter, choose Compare, and set this month against last month. The table gains a Difference column ([Google's filtering docs](https://support.google.com/webmasters/answer/17011165)).
2. On the Pages tab, sort by Difference. Top rows are candidates to double down on; bottom rows are slipping.
3. Set the Query filter to Non-branded to see which posts bring in strangers (it isn't available for sites with few impressions).
4. Add each post's docs clicks, signups and first API calls from your analytics, as our [content ROI guide](/blog/developer-tool-content-roi-beyond-pageviews) describes.

| What you see | Decision |
| --- | --- |
| Non-branded clicks and docs clicks both rising | Double down: schedule a part 2 or a sister integration guide |
| High impressions, low CTR | Rewrite the title and description, as [Google suggests](https://support.google.com/webmasters/answer/17010961) |
| Traffic, but almost no clicks to docs | Fix the CTA and the next step, not the topic |
| Broken code or outdated versions | Refresh: rerun the code, update versions, then change the date |
| Flat for 90 days, with no product movement or comments | Cut: stop writing that topic or format |
| A timely post past its moment | Leave it, and link it to an evergreen piece |

**Key pointers:**

* Write each decision into the sheet during the meeting, not after it.
* Retire at least one recurring format a quarter if it never moves developers to the docs.

## The spreadsheet columns to set up today

Start with the eight columns from the 12-week template, then add the ones below. In Google Sheets, select a column and choose Insert, then Dropdown, to lock its values ([Google Docs Editors Help](https://support.google.com/docs/answer/186103)).

**Template: the extra columns**

| Column | Values |
| --- | --- |
| Job | Dropdown: discover, evaluate, activate, expand |
| Shelf life | Dropdown: evergreen, timely |
| Source | Link to the query, ticket, issue, thread or prompt log |
| Release anchor | Version number, or none |
| Status | Dropdown: idea, outline, draft, tech review, edit, scheduled, live |
| Review due | Date, taken from the SLA table |
| Live URL | Link |
| 30-day result | Non-branded clicks, docs clicks, signups |
| Decision | Dropdown: double down, refresh, keep, cut |

**Key pointers:**

* Make Source and Reviewer required: no link and no reviewer means no row.
* Fill the 30-day result and Decision columns at the monthly review, never from memory.

## FAQ

### How far ahead should a devtool plan its content?

Plan 12 weeks at a time, firm for the first four. Enter known release dates first, and hold one open slot a month for timely topics.

### How many blog posts should a devtool publish per month?

As many as your engineer reviewers can check: often two a month for a solo founder and one a week for an in-house writer. Two tutorials with working code beat eight with broken code.

### What should a devtool content calendar include?

One row per piece, with the week, title, type, target query or AI prompt, source link, owner, reviewer, status, channels, CTA and 30-day result. The source proves demand, and the reviewer protects accuracy.

### Should the content calendar follow the product roadmap?

Anchor launch posts and migration guides to it, but don't let it fill the calendar. Most weeks should answer questions developers already ask in search, tickets, issues and threads.

### What is the difference between evergreen and timely developer content?

Evergreen content, like tutorials and comparisons, earns search traffic for months. Timely content reacts to news, such as a framework release, and gets most of its attention in a short window.
